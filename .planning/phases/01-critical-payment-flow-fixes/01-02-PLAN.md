<objective>
Fix three M-Pesa payment bugs across two files. All three bugs currently cause production M-Pesa payments to fail or trigger dangerous retry loops:

1. PAY-02: `settings.py` lines 262-265 build all three M-Pesa webhook URL defaults from `FRONTEND_URL` (`https://rumia.co.ke`). The Next.js frontend does not handle M-Pesa POST webhooks. In production, Safaricom's callbacks hit the frontend server, receive HTML/404, and all STK push payments remain stuck `pending` forever. Fix: introduce `BACKEND_API_URL` env var and rebuild the three URL defaults from it.

2. PAY-03: `_update_transaction_from_stk_push` (mpesa_webhooks.py line 218) checks `if transaction_obj.status == 'success':` without a row lock. Two concurrent M-Pesa retry deliveries can both pass this guard, causing double rent credit and duplicate receipts. Fix: wrap the status check and update inside `with transaction.atomic(): ... select_for_update()`.

3. PAY-04: The outer `except Exception` in `_handle_stk_push_callback` (mpesa_webhooks.py line 170-176) returns `status=500`. Safaricom treats non-2xx as delivery failure and retries indefinitely — combined with PAY-03's missing row lock, this creates a double-processing risk. Fix: always return HTTP 200 with the standard M-Pesa acknowledgment body.

Purpose: Without PAY-02, no M-Pesa payment ever completes. Without PAY-04, every internal exception triggers an infinite Safaricom retry storm.
Output: Modified Backend/rumi/settings.py and Backend/payments/mpesa_webhooks.py.
</objective>

**Fix 1 — PAY-03: Add select_for_update() to _update_transaction_from_stk_push**

The method at line 212 receives a `transaction_obj` that was already fetched by the caller. Inside this method, re-fetch the object with a row lock before performing the idempotency check.

Current code (lines 216-227):
```python
        try:
            if transaction_obj.status == 'success':
                return JsonResponse({'status': 'already_processed'}, status=200)

            transaction_obj.status = 'processing'
            transaction_obj.mpesa_receipt_number = payment_info.get('receipt_number')
            transaction_obj.mpesa_phone_number = payment_info.get('phone_number')
            transaction_obj.metadata = payment_info
            transaction_obj.save()
```

Replace with:
```python
        try:
            with transaction.atomic():
                # Re-fetch with a database row lock to prevent race condition from
                # concurrent M-Pesa retry deliveries (Safaricom retries on non-200).
                transaction_obj = Transaction.objects.select_for_update().get(
                    pk=transaction_obj.pk
                )
                if transaction_obj.status == 'success':
                    return JsonResponse({'status': 'already_processed'}, status=200)

                transaction_obj.status = 'processing'
                transaction_obj.mpesa_receipt_number = payment_info.get('receipt_number')
                transaction_obj.mpesa_phone_number = payment_info.get('phone_number')
                transaction_obj.metadata = payment_info
                transaction_obj.save()
```

Important: `transaction` (lowercase) is already imported at line 21 as `from django.db import transaction`. Use it directly — do NOT add a duplicate import. The `with transaction.atomic():` block must wrap both the `select_for_update()` re-fetch AND the subsequent `.save()` call (they must be in the same atomic block for the lock to be effective).

Also fix the inner `except Exception` block at the bottom of `_update_transaction_from_stk_push` (around line 262-264):
